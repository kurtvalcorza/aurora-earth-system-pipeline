# Release verification

`tutorials/aurora_earth_system_colab.ipynb` (`E2E`, **standalone** carrier) is a **release candidate** until the exact
notebook revision has executed top-to-bottom in a clean supported runtime. Unit tests, JSON validation, code-cell
compilation, the generator parity checks and `tools/validate_release_assets.py` are necessary checks but are **not**
runtime evidence under DIMER Notebook Specification 2.2 (REL8). This file is the durable release-gate record.

Since the fix of review findings AUR-M1..M4 / AUR-m1..m6 (Notebook Review Framework v1, review PR #14) the notebook is
generated by `tools/build_notebook.py` /3: nothing is installed into the notebook kernel, a pinned `uv` builds an isolated
CPython 3.12.12 environment from `tutorials/requirements-colab.lock.txt` with `--require-hashes`, and every learner cell
runs one stage of the carried `tools/tutorial_stages.py` in its own process. The procedure below describes that notebook;
the recorded executions further down are of the previous, in-kernel version and say so, except the 2026-10-03 hosted
Colab T4 run of this notebook (commit `a59bed4`, blob `cfa631b6`).

## Automatic coverage (static, every pull request)

CI runs `tools/validate_release_assets.py`, which checks:

- notebook JSON parses; every code cell compiles as plain Python (no `%`/`!` magics); no persisted outputs or
  execution counts; no unresolved placeholder markers; every code cell is preceded by an explanatory markdown cell;
- the two tutorial notebooks are exactly the generated tutorial and the supplemental notebook, both named in
  `tutorials/README.md`; `metadata.dimer` of the tutorial declares `E2E`, spec `2.2`, a §3.3 pedagogical mode,
  `standalone: true`, `requires_dimer_worker: false` and `generated_from` (repository, revision, module SHA-256, file
  digests, generator);
- the standalone carrier (ST1–ST8, SRC4, PAR1–PAR4): exactly one carrier cell whose `CARRIED_FILES` equal the
  repository files (the 4 package modules, the stage runner, the lock, the snapshot manifest, the licence and
  `source.json`) and whose `CARRIED_HASHES` are correct, verified in the cell before use; the notebook byte-identical
  (on LF) to the generator output for its recorded revision;
- the isolated install (RUN10, ENV6): the lock pins every `pyproject.toml` pin with hashes, was compiled wheel-only for
  manylinux x86_64; the `uv` wheel is pinned by URL, size and SHA-256; the only installer call is
  `uv pip install --python <isolated env> --require-hashes`; no kernel cell imports a model library, `importlib`,
  `pickle` or runs `pip`; `run_stage` re-raises a stage's own error message;
- the canonical stages called exactly once each in order (`weights`, `runtime`, `data`, `rollout`, `frozen`, `adapt`,
  `evaluate`, `forecast`, `reload`, `bundle`, then the optional `activity`), the BYOD fields `USE_BYOD` / `BYOD_PATH`
  driving the `data` stage in one cell, the stage runner's required public-API calls, checks and refusals (the
  workflow-length check, the frozen-pipeline check, the default-path expectation, the reload tolerance, the provenance
  fields `served_from_pickle: False`, `remote_code_executed: False` and the data base URL) and the expected outputs;
- the guided layer (GDL1–GDL15): how to use, the input → model → output table, roadmap, fast path, glossary, section
  tags on every numbered heading, minimum counts of prediction prompts, notes, expected results and collapsed answers,
  the optional activity gated off and placed after the canonical path, troubleshooting, the conclusion template, and
  titled, collapsed infrastructure cells; no learner prose instructs a runtime restart and no timing is stated without
  its environment;
- `MODEL_ID`/`MODEL_REVISION` bound only in the carried package, the revision a 40-hex immutable commit, and the same
  identity string in `README.md`, `MODEL_CARD.md` and `docs/WEIGHTS.md` with no stray revisions (the upstream
  package's default revision for the small checkpoint is the one allowed second hash);
- forbidden patterns (credential-in-URL, any `git clone` / `github.com` / repository import on the primary path, a
  mutable `revision='main'`, `trust_remote_code=True`, `pickle.load` or `torch.load(` without `weights_only=True`,
  `extractall(`, source or unhashed installs) in the kernel cells and the carried files;
- `STATUS.md`, `README.md` and `tutorials/README.md` agree on one release-status token and no document makes an
  unsupported release-grade, production-readiness or benchmark claim;
- `MODEL_CARD.md` front matter (`model_card_spec: "1.1"`), single H1, the 19 required headings in order, and the
  immutable provenance section.

CI also runs `ruff check src tests tools`, `tools/build_notebook.py --check`, and the offline unit suite (crafted
pickles, temporary manifests, synthetic windows, an injected fetcher and a stand-in `aurora` model for the stage-runner
tests; no weights and no real model — `tests/test_model_backed.py` is skipped there). These are source/provenance and
unit checks. They are **not** execution evidence.

## Supported release verification procedure

Before changing the registry status from `Candidate` to `Release-grade`:

1. resolve the exact PR/commit head under review and confirm static CI is green;
2. open that exact notebook revision in a new Linux x86_64 CPU or CUDA runtime (Colab, or a fresh-container executor
   above) with **no repository checkout**, an empty Hugging Face cache, and no pre-staged files under `weights/`
   (the standalone path writes the manifest itself, stages all three listed files from the Hub, audits and converts
   both pickles, and fetches the 57 pinned WeatherBench 2 objects, so the directory may not be seeded);
3. choose **Run all once** without editing implementation cells (form parameters at their defaults: `USE_BYOD = False`,
   `BYOD_PATH = ''`, `ORIGIN = 1`, `ROLLOUT_STEPS = 4`, `MAX_LEAD_STEPS = 4`, `EPOCHS = 6`, `LEARNING_RATE = 1e-3`,
   `TRAINABLE = 'lora'`, `RUN_ACTIVITY = False`). **The run must complete in one pass**: a restart of the interpreter, a
   second pass or a manual re-run of any cell means the run is not `Run all` evidence (RUN1, RUN10) — record it with
   its pass count, never as PASSED;
4. verify that Section 2 reports the carried files verified and the revision recorded in
   `metadata.dimer.generated_from`, that the isolated environment reports CPython 3.12.12, and that Section 4 reports
   `versions_match_lock: True` for `torch==2.14.0`, `microsoft-aurora==2.0.1`, `timm==1.0.29`, `einops==0.8.2`,
   `xarray==2026.7.0`, `netCDF4==1.7.4`, `numcodecs==0.17.0`, `numpy==2.5.3`, `safetensors==0.8.0` and
   `huggingface-hub==1.32.0`;
5. verify every default-path stage completes:
   - Section 3: the 3 manifest entries fetched from `microsoft/aurora` at the immutable revision, 3 verified files, both
     **pickle audits** (checkpoint globals `collections.OrderedDict` / `torch.FloatStorage` /
     `torch._utils._rebuild_tensor_v2`, static globals `numpy.core.numeric._frombuffer` / `numpy.dtype`, 0 violations,
     audit digests `e7b998d0…` / `aeec283f…`) and both converted files (`fc03b5fc…` 451,230,408 bytes; `9bd430b6…`
     12,459,136 bytes);
   - Section 5: 4 windows on a (121, 240) grid, 8 steps each, 24 forecast origins, the time span 2018-12-31 to
     2021-10-01, digest `4ee4be11…`, `steps_needed_for_these_settings: 6`, the sample NetCDF (6 steps, about 48 MB),
     and five refusals (wrong levels, odd longitude count, implausible temperature, irregular time spacing, a 5-step
     window for these settings);
   - Section 6: a 4-step roll-out from origin 1 of the test window with shape (120, 240), `adapted: False`,
     `lora_b_max_abs: 0.0` and `repeat_identical: True`;
   - Section 7: persistence and the frozen model per lead (on the sample: 6-hour mean skill ≈ 1.57 with 1 of 9
     variables beating persistence), written to `outputs/aurora_earth_system_frozen_test.json`;
   - Section 8: `lora_b_max_abs: 0.0` at the start, epoch 0 as the frozen model, 540,672 trainable of 113,338,256
     parameters, 12 training samples, a six-epoch history with validation loss falling from ≈ 0.18 to ≈ 0.05, and the
     adapter (80 tensors, 2,173,200 bytes);
   - Section 9: the three-way comparison with the adapter rebuilt from files and the outcome line (on the sample
     ≈ 0.90 versus ≈ 1.57 at 6 h, 1 → 6 variables beating persistence; the stage stops if the default configuration
     does not improve);
   - Section 10: a 4-step forecast from origin 3 and `outputs/aurora_earth_system_forecast.nc` with 9 variables;
   - Section 11: `reload_verification: PASSED` with maximum differences at or near 0;
   - Section 12: `outputs/aurora_earth_system_result.json` with the provenance block and the SHA-256 of every output;
6. verify the exports exist and the interpretation section matches the observed path; for the optional journeys, run
   the activity (`RUN_ACTIVITY = True`), one BYOD positive run with the Section 5 sample file as `BYOD_PATH`, and one
   BYOD negative run with a 5-step window (refused in Section 5), and record each;
7. record the notebook Git blob id, commit, runtime (platform, kernel Python, isolated-environment Python, PyTorch,
   device), the model identifier and immutable revision, whether the caches were clean, the pass count, outcome,
   produced outputs, the observed metrics (as observations, not a benchmark) and any warning or applicable `SHOULD`
   deviation in the tables below;
8. record no access tokens or other secrets.
