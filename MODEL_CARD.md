#### Description

`microsoft/aurora` at revision `a96afd7ee6d65e3bd2d476f3be798a25a56f2296` is the weight repository of Aurora, the Earth-system foundation model of Bodnar, Bruinsma, Lucic et al. (Nature 641, 2025): a 3D Swin transformer backbone between a Perceiver encoder and decoder that takes two consecutive analyses — surface variables `2t`, `10u`, `10v`, `msl`; atmospheric variables `t`, `u`, `v`, `q`, `z` on 13 pressure levels; static fields `lsm`, `z`, `slt` — on a global equiangular grid and returns the state six hours later, with the encoder patching the grid at 4 × 4 and pooling the levels into latent levels. The file packaged here, `aurora-0.25-small-pretrained.ckpt` (451,339,106 bytes, SHA-256 `f80f78de…`), is the small pretrained variant: embedding dimension 256, encoder/decoder depths (2, 6, 2), heads (4, 8, 16) / (16, 8, 4), 112,797,584 parameters in float32, trained at 0.25° with a 6-hour step and `max_history_size` 2. The upstream class `AuroraSmallPretrained` carries the note "should only be used for debugging"; the 1.3 B-parameter pretrained, fine-tuned, 12-hour, wave, air-pollution and 1.5 checkpoints in the same repository are not packaged. The architecture provides LoRA adapters (rank 8) on the query/key/value and output projections of every backbone attention block — 80 tensors, 540,672 parameters — zero-initialised so that a model built with `use_lora=True` is the pretrained model until trained.

What this repository adds is the `AuroraPipeline` class in `src/aurora_earth_system_pipeline/pipeline.py`: manifest verification of the 3-file Hub snapshot before any model library is imported (`verify_snapshot`, which also checks the converted files against their pinned digests when present), fresh-clone staging at the pinned revision (`stage_missing_files`), a **static audit of each pickle** that lists every global it would import with `pickletools` and refuses anything outside a per-file allow-list (`audit_pickle`, digests pinned), a **one-time conversion** of the checkpoint through torch's weights-only unpickler and the upstream compatibility shim into a strictly loaded model whose state dict is saved as safetensors, and of the static fields through a two-name `find_class` allow-list into a second safetensors file (`convert_model`), model construction from the installed `microsoft-aurora` package (`build_model`), window validation with named ceilings (`validate_inputs`), autoregressive forecasting to eight steps (`predict`), latitude-weighted RMSE per variable and lead against the window's later analyses with the persistence baseline scored alongside (`evaluate`), bounded LoRA fine-tuning on one-step forecasts (`adapt`), and a safetensors adapter artifact that is digest-verified before deserialization (`save_artifact`, `from_artifact`). `samples.py` fetches four two-day windows of ERA5 at 1.5° from WeatherBench 2 as 60 digest-pinned Zarr objects decoded with `numcodecs` (no Zarr, xarray or cloud SDK on the download path) and reads/writes NetCDF windows for BYOD; `metrics.py` holds the RMSE, the persistence baseline and the skill summary.

Two things about this profile are stated rather than hidden. **The tutorial resolution is not the training resolution.** ERA5 at 1.5° (240 × 121, with poles) is what a tutorial can fetch — about 196 MB for four windows against roughly 430 MB per atmospheric variable per window at 0.25° — and the model handles the grid (the last latitude row is cropped to a multiple of the patch size, 121 → 120, exactly as 721 → 720 at 0.25°), but every measurement on it is an out-of-distribution measurement: the frozen small model has a 6-hour latitude-weighted RMSE above persistence for eight of nine variables. The card reports that number beside the adapted one and claims nothing about native-resolution skill; the converted model's faithfulness is established separately with upstream's own regression fixture at 400 × 800 (see *Runtime*). **The tutorial's reference is ERA5 itself** — the analyses the model is asked to forecast — which is the standard verification target for data-driven weather models and also means the evaluation inherits ERA5's own errors relative to observations.

#### Intended Use and Limitations

###### Primary Intended Uses

Two tasks are exposed. **Short-range global forecasting:** input is one window — two consecutive 6-hourly analyses (plus later ones for evaluation) of the nine variables and three static fields on a global equiangular grid of 17..721 latitudes (90 → −90, a multiple of 4 or one more) and 32..1440 longitudes (0 → 360, a multiple of 4), the 13 standard pressure levels, SI units; output is the forecast at 1..8 lead steps of 6 hours as gridded fields of the same nine variables on the rows the patch size covers. **Adaptation to local gridded reference data:** given at least one window of analyses on one grid, the pipeline fine-tunes the LoRA tensors (optionally also the token embeddings and decoder heads) on one-step forecasts, predicts with the adapted model and exports the changed tensors as a 2 MB adapter. Envisioned application domains are Earth-system workflows where a foundation forecast model is a starting point — adapting it to a coarser or regional grid, to a different analysis product, or to a variable set with the same names; teaching and evaluating foundation-model fine-tuning for weather; and prototyping a forecast service whose skill is then measured against persistence and a proper baseline on the operator's own data. In a larger system the pipeline is a single-model forecaster and an adaptation baseline whose output feeds a verification workflow or a forecaster's judgement; it is not an operational forecast system, an ensemble, or a data-assimilation component.

###### Primary Intended Users

Intended users are atmospheric and climate scientists, Earth-system data engineers and machine-learning engineers who work with gridded reanalysis or analysis products, in research, internal enterprise, or the DIMER model workbench. The pipeline assumes its users understand that a data-driven weather model learned the statistics of ERA5 at 0.25° and that resolution, variable set, level set and units are part of that contract; that persistence is a strong baseline at short leads and that a forecast is only worth reporting beside it; that consecutive analyses are near-duplicates, so splits must be by period; that RMSE against a reanalysis inherits the reanalysis's own errors; that autoregressive roll-outs accumulate error and can drift beyond the leads tested; and that the small checkpoint is a testing variant whose skill is far below the production model's at any resolution.

###### Out-of-scope use cases

1. **Capability boundary:** the pipeline forecasts the nine Aurora variables at 6-hourly leads and fine-tunes LoRA (and optionally embeddings and heads) on one-step forecasts. It does not run the 1.3 B-parameter production checkpoints or the wave, air-pollution, 12-hour, 0.1° or 1.5 variants; it does not do ensemble forecasting, tropical-cyclone tracking, roll-out (multi-step) fine-tuning, data assimilation, downscaling, or verification against observations; it does not reproduce the published WeatherBench scores; and it does not verify that an input window is dynamically consistent or real.
2. **Input boundary:** windows are `{lat, lon, levels, times, surf, atmos, static}` mappings — latitudes spanning the poles, longitudes covering the full circle, exactly the 13 standard levels, 3..64 analyses spaced exactly 6 h apart, finite float values within the plausibility ranges (e.g. `2t` 150–350 K, `msl` 85–110 kPa, `q` −10⁻³–0.1 kg/kg), at most 8 roll-out steps. Regional (non-global) grids, other level sets, other variables, hourly or 12-hourly spacing, and missing static fields are not inputs.
3. **Decision boundary:** not for autonomous action on a forecast — issuing warnings, routing, scheduling, energy dispatch, or any use where a wrong forecast has consequences for people or assets — without verification against the deployment's own reference over a representative period and a forecaster's review. A forecast from this pipeline is an experiment output, not guidance.
4. **Provenance boundary:** not for settings that require the exact upstream serialized objects to be executed, or that forbid any one-time unpickling of a third-party checkpoint even through a restricted loader after a static audit; the trust boundary is documented under *Mitigations* and in `docs/WEIGHTS.md`.

#### Factors

###### Groups

The pipeline's inputs are gridded atmospheric fields, not records about people, so age, gender, skin type and socioeconomic status are not attributes of any input and no demographic evaluation applies. The relevant groups are geographic and meteorological: skill differs by latitude band (the RMSE is cos-latitude weighted precisely because an equiangular grid over-represents the poles), by land versus ocean, by season, and by regime (tropical cyclones, blocking, fronts), and a global mean hides all of it. Upstream reports per-region and per-variable scores for the production model; this repository measures one two-day window per role in three seasons of three years at one resolution, and reports global means. Whose weather is forecast well is therefore unmeasured here — and a deployment serving a region should measure it there.

###### Instrumentation

There is no physical sensor in this pipeline. The instruments are the analysis system that produced the inputs — ERA5's assimilation of observations into a model background, with its known biases near the surface, in the tropics and in data-sparse regions — and the regridding (WeatherBench 2's conservative regridding to 1.5°), both of which the model sees as truth. A different analysis product (a NWP model's own analysis, a different reanalysis) shifts the input distribution and the verification target at once. The model's own instrument is its patching: 4 × 4 grid cells per token, so at 1.5° a token spans 6° × 6° of the Earth, thirty-six times the area it was trained on.

###### Environment

Operating environment: Python 3.12 with `torch==2.14.0`, `microsoft-aurora==2.0.1`, `timm==1.0.29`, `einops==0.8.2`, `xarray==2026.7.0`, `netCDF4==1.7.4`, `numcodecs==0.17.0`, `numpy==2.5.3`, `safetensors==0.8.0`, `huggingface-hub==1.32.0` (`pyproject.toml`); `microsoft-aurora` brings `scipy`, `pydantic`, `azure-storage-blob` and others as its own dependencies, none used here. The model runs in float32; `device` defaults to `cpu` and the notebook selects CUDA when visible. Verified locally in a dedicated Windows venv on `torch 2.14.0+cpu`; the recorded run is under "Runtime" (conversion 5.3 s, load 1.4 s, one 6-hour step at 1.5° in about 0.7 s, a 6-epoch LoRA adaptation on 12 one-step samples in 212 s, a native-resolution-class forward at 400 × 800 in double precision in 25.6 s). Memory: about 2 GB for the model, the four windows and the training graph at 1.5°; a native 0.25° window needs several GB more. Data environment: the model assumes ERA5-like analyses at 0.25°; it degrades, without any error, at other resolutions and on other products, which the tutorial demonstrates rather than hides.

#### Metrics

###### Performance Measures

The pipeline reports, exactly as `metrics.forecast_metrics` names them: for each of the nine variables and for `z500` (geopotential at 500 hPa, the customary headline) at each lead, `model` — the latitude-weighted RMSE (cos-latitude weights normalised to unit mean; atmospheric variables averaged over the 13 levels) against the analysis at the valid time, averaged over every forecast origin the window allows — `persistence`, the same score for the latest analysis carried forward, and `skill`, their ratio (below 1 beats persistence); plus a per-lead `summary` with the mean skill over the nine variables and the count of variables beating persistence. Three comparison points are read together: the **persistence baseline** (no model; at 6 h a strong one, and for `2t` better again at 24 h as the diurnal cycle re-aligns), the **frozen foundation model** (LoRA at zero), and the **adapted model**. Every number in this repository is sample-sanity evidence on one two-day window per role from one seeded run with no dispersion estimate; no number from the Aurora paper or WeatherBench 2 is reproduced or claimed.

###### Decision thresholds

There is no classification and no decision rule in the pipeline: `predict` returns continuous gridded fields and applies no threshold. The limits that *were* fixed during development are input-contract limits, not decision thresholds — the grid bounds `MIN_GRID = (17, 32)` and `MAX_GRID = (721, 1440)`, the patch-size divisibility rules, `MAX_STEPS_PER_WINDOW = 64`, `MAX_ROLLOUT_STEPS = 8`, the exact 6-hour spacing and the plausibility ranges — chosen so that a rejection names a real defect and an acceptance never means "meteorologically sensible". An operator who needs a threshold (a warning criterion on wind speed, an acceptable RMSE for a downstream use, a maximum lead before a forecast is discarded) must set it from verification against their own reference and own it. `adapt` selects the epoch with the lowest validation loss, which is the only selection this repository performs.

###### Approaches to uncertainty and variability

Reported metrics come from **one window per role**: two training windows, one validation window (epoch selection only) and one test window from three distinct years and seasons, each scored over every origin it allows (three origins at 24 h, six at 6 h). No cross-validation, bootstrap, ensemble or repeated-run averaging is performed, and no dispersion is reported — with two days of one month, any interval would be dominated by the synoptic situation. A caller who needs one evaluates over many windows across seasons and years, and owns that design. Sources of run-to-run variability: LoRA-A initialisation and sample shuffling are seeded through `torch.manual_seed` and a seeded generator; the data are pinned bytes; the forward is deterministic on CPU (the same origin forecast twice is bit-identical); non-deterministic GPU kernel selection is not controlled, and multithreaded CPU training is not bit-reproducible either (two runs of the same notebook differed by 0.06 K in the adapted 6-hour `2t` RMSE while agreeing on every frozen number). The pipeline produces no forecast uncertainty — no ensemble, no spread, no calibration — and the upstream ensemble checkpoint is not packaged.

###### Mitigations

1. **Supply-chain integrity:** `MODEL_ID` and the 40-hex `MODEL_REVISION` are module constants; `verify_snapshot()` checks `modelId`, `revision`, and the byte size and SHA-256 of all 3 manifest entries before any load, additionally asserts both source files' digests against the package constants, and raises on the first mismatch (tests flip a digit, change the identity and delete a file and assert each raises). `stage_missing_files()` fetches only manifest-listed files absent on disk, only at `MODEL_REVISION`, only when `allow_download=True`, and refuses a manifest naming another model. `.gitattributes` carries `weights/** -text`.
2. **Executable serialization handled explicitly (asset spec §11.2):** neither pickle is loaded by the runtime path. `audit_pickle` lists every global each would import with `pickletools` (the checkpoint: `collections.OrderedDict`, `torch._utils._rebuild_tensor_v2`, `torch.FloatStorage`; the static file: `numpy.core.numeric._frombuffer`, `numpy.dtype`) and refuses anything else; the audit digests are pinned. `convert_model` runs size → digest → audit on each file before loading it: the checkpoint through `torch.load(weights_only=True)` (torch's restricted unpickler, which cannot construct arbitrary objects), then the upstream `_adapt_checkpoint` shim and `load_state_dict(strict=True)` into `AuroraSmallPretrained`; the static file through a `pickle.Unpickler` whose `find_class` allows exactly the two numpy names. Both are re-saved as safetensors. Tests craft archives with `os.system` and a plain pickle with `builtins.eval` and assert each is refused before anything is unpickled, and that the restricted unpickler refuses a global outside its list.
3. **Deterministic, digest-pinned serving files:** the conversion reproduces the same digests on every run (build, smoke, executed notebook); `verify_converted` checks sizes and SHA-256 against `CONVERTED_SHA256` / `CONVERTED_BYTES`; the model loads with `strict=True` (or, with LoRA, with exactly the 80 LoRA tensors missing and nothing unexpected) and a parameter-count check. With `require_source=False` (the DIMER-hosted case) the converted files alone are accepted, still digest-verified.
4. **Conversion fidelity evidence, stated with its limits:** the converted model reproduces upstream's recorded regression output for this checkpoint (400 × 800 grid, 7 levels, double precision, the static fields interpolated as upstream's test does) with relative mean deviations 1.2×10⁻⁷ (`msl`) to 3.5×10⁻⁵ (`10v`), all within the upstream tolerances (1×10⁻⁴ / 5×10⁻³). Measured under one `microsoft-aurora` version; behaviour under the version that produced the checkpoint was not measured.
5. **Data integrity:** every WeatherBench 2 object the tutorial fetches (Zarr chunks, `.zarray` descriptors, coordinates — 57 objects, about 196 MB) has its byte size and SHA-256 pinned in `WB2_OBJECTS`; `fetch_object` refuses a mismatch before decoding, decodes with `numcodecs` only, and never follows a listing or a mutable index. The time axis is computed from the store's fixed epoch and verified uniform at build time.
6. **Artifact integrity and scope:** the adapter is safetensors, not a pickle. `load_artifact` validates the manifest **before** deserialising anything: the artifact format and `format_version`, the recorded base model id, revision and converted-base digests, exactly one weights entry named `adapter.safetensors` that resolves inside the artifact directory, an `adapter.trainable` that is exactly `lora` or `lora+heads`, and a tensor list equal to the exact set that scope may change on this model (the 80 LoRA tensors, plus the encoder token embeddings and decoder heads for `lora+heads`); the safetensors keys must then equal that set and every shape must match, and `from_artifact` builds the LoRA model from the validated mode rather than from tensor names. The weights file's SHA-256 is checked against the adjacent manifest — it detects corruption or drift of the file relative to that manifest, not authenticity: an actor who can replace both files can make them agree.
7. **Input integrity:** `predict`, `evaluate`, `adapt` and `validate_inputs` route through one checker, so their acceptance criteria cannot diverge; it rejects missing groups and variables, wrong shapes, non-finite values, out-of-range values, non-monotonic or non-uniform coordinates, grids that do not span the poles or the full circle, grids outside the ceilings or off the patch size, wrong level sets, too few or too many steps, and non-6-hourly spacing; ascending latitudes are flipped and reported. `validate_dataset` additionally rejects duplicate names and mixed grids.
8. **Import boundary:** verification, the static audits and validation run before `torch`, `aurora`, `safetensors`, `timm`, `einops` or `huggingface_hub` are imported (DIMER RTM-001); `tests/test_import_boundary.py` fails if a rejected request reaches a model library, and an AST check fails if any of them is imported at module level.
9. **Statistical mitigations:** roles are assigned by window from different years and seasons, never by shuffling steps; the persistence baseline is scored on the same origins as every model number; validation is used for epoch selection only and the test window for nothing but the final evaluation; the notebook asserts the adapted 6-hour mean skill is below the frozen model's and that more variables beat persistence.
10. **Honest scope:** validation is labelled structural, the resolution is labelled out-of-distribution, the small checkpoint is labelled a testing variant, the persistence column is printed before any model number, and no upstream benchmark is claimed.

Not implemented, and therefore not claimed: no roll-out fine-tuning, no protection against forgetting, no ensemble or uncertainty, no climatology or operational-forecast baseline, no verification against observations, no regional evaluation, and no measurement at the native resolution beyond the regression fixture.

###### Risks and harms

1. **A conversion can be subtly wrong:** the evidence is the regression-fixture parity and the physics-free structural checks, under one `microsoft-aurora` version. A future package version that changed a block's semantics while keeping its parameter names would load strictly and silently compute something else; the exact pin is the control, and the parity test is the check to re-run before changing it.
2. **A pickle audit is an allow-list, not a proof:** the static audit bounds what the unpickler can name; torch's weights-only unpickler and the two-name `find_class` list bound what it can construct. The digest pins tie the audited bytes to the loaded bytes, and each unpickle happens once, in the operator's environment.
3. **Resolution read as model quality:** the frozen model's loss to persistence at 1.5° is a resolution story; a reader who carries it to 0.25° draws the wrong conclusion, and a reader who carries the adapted skill to other months draws an unsupported one.
4. **Catastrophic forgetting and drift:** fine-tuning on twelve one-step forecasts from two windows improves those conditions and says nothing about other seasons or regimes; roll-outs beyond the leads tested can drift, and nothing in the output flags it.
5. **Near-duplicate leakage:** consecutive analyses are near-duplicates; a split over shuffled steps makes memorisation look like skill. Neither the model nor this repository can detect a leaking split the operator builds.
6. **Confident nonsense outside the domain:** a regional grid padded to look global, a different analysis product, or wrong units are forecast with the same silent confidence; validation catches shapes and ranges, not meaning.
7. **Reanalysis as truth:** ERA5 errors relative to observations — near the surface, in the tropics, over data-sparse regions — become invisible when ERA5 is both input and target.
8. **Proprietary data in a hosted runtime:** the realistic confidentiality failure is an unreleased analysis or an embargoed dataset uploaded to a cloud notebook. Inference is local, but the runtime may not be the operator's.

###### Use cases

The model must not be used to issue or inform weather warnings, aviation, marine, agricultural, energy or emergency decisions, or any forecast presented as guidance, without verification against the deployment's own reference over a representative period and a qualified forecaster's review; it must not be used as evidence about Aurora's native-resolution skill, which this repository does not measure; it must not be used to load or execute the upstream pickles in any way other than the audited, digest-verified, one-time conversion this repository performs; it must not be used to redistribute ERA5 or WeatherBench 2 data without the Copernicus attribution and licence terms; and it must not be used in any way that breaches the MIT terms of the upstream weights or the DIMER deployment terms.

## Input/output contract

- `AuroraPipeline.from_pretrained(device="cpu", weights_dir=None, allow_download=False, require_source=True, use_lora=False, report=None)`: stages and verifies the snapshot, audits and converts both pickles when the safetensors are absent (reporting through `report`), builds `AuroraSmallPretrained(use_lora=…)` from the installed package and loads the safetensors strictly (with LoRA: exactly the 80 LoRA tensors left at their zero initialisation). `require_source=False` accepts digest-verified converted files without the pickles or the manifest.
- `predict(window, *, origin=None, steps=1) -> dict` with `model` (id, revision, key, `adapted`), `name`, `origin_time`, `shape`, `lat`, `lon`, `units`, `forecasts` (per lead: `lead_hours`, `valid_time`, `surf` fields (H', W), `atmos` fields (13, H', W)), `seconds`.
- `evaluate(window, *, max_lead_steps=1, origins=None) -> dict`: `n_origins`, `leads`, `grid`, `variables` (per variable and `z500`, per lead: `model`, `persistence`, `skill`), `summary` (per lead: `mean_skill`, `variables_beating_persistence`), `metric`, `units`, `seconds`.
- `adapt(train, val=None, *, epochs=6, lr=1e-3, trainable="lora", seed=0, progress=None) -> dict`: bounded AdamW fine-tuning on one-step forecasts; returns the trainable set and counts, hyperparameters, `loss_scales`, sample counts, `best_epoch`, per-epoch `history` (epoch 0 = the frozen model, each with `train_loss`, `val_loss` and the validation metrics) and `seconds`. `trainable="lora+heads"` also unfreezes the encoder token embeddings and decoder heads.
- `save_artifact(output_dir, metadata=None) -> Path` writes `adapter.safetensors` (the trained tensors) + `manifest.json` (format, base model id/revision/key and converted digests, adaptation record, history, tensor names, file size and SHA-256); `from_artifact(...)` / `load_artifact(...)` verify all of that before deserialising and rebuild with LoRA when the adapter carries LoRA tensors.
- `native_static_fields() -> dict` returns the upstream 0.25° static fields (721, 1440) from the converted file for native-resolution use.
- `validate_inputs(window) -> dict` (`name`, `shape`, `n_steps`, `times`, `forecast_origins`, `flipped_latitude`, `ignored_variables`, `resolution_degrees`, `native_resolution`) and `validate_dataset(windows, *, min_windows=1, min_steps=3) -> dict` (normalised `windows`, counts, `shape`, `time_span`, `digest`) raise exactly what the execution path would raise. `fetch_sample_dataset(cache_dir=None)` / `fetch_sample_window(name)` / `fetch_object(key)` are the pinned-data primitives; `load_byod_dataset(path)` (NetCDF) and `write_window_netcdf(window, path)` the BYOD I/O; `persistence_only(window, max_lead_steps)` the baseline alone; `window_digest` / `dataset_digest` pin data.
- `audit_pickle(path, allowed=…)`, `convert_model(path=None)`, `verify_converted(path=None)` and `build_model(use_lora=…)` are the serialization primitives.
- Constants: `SURF_VARS`, `ATMOS_VARS`, `STATIC_VARS`, `LEVELS` (13), `TIMESTEP_HOURS = 6`, `HISTORY_STEPS = 2`, `PATCH_SIZE = 4`, `NATIVE_SHAPE = (721, 1440)`, `MIN_GRID = (17, 32)`, `MAX_GRID = (721, 1440)`, `MAX_STEPS_PER_WINDOW = 64`, `MAX_ROLLOUT_STEPS = 8`, `PARAMETER_COUNT = 112797584`, `STATE_TENSORS = 332`, `LORA_TENSORS = 80`, `LORA_PARAMETERS = 540672`, `RANGES`, `LOSS_SCALES`, `ARTIFACT_FORMAT = "org.valcorza.aurora-earth-system.adapter.v1"`.

## DIMER deployment notes

| Field | Status |
|---|---|
| **DIMER status** | **Planned / conditional** — the `.ckpt` asset-format and deserialization-trust review DIMER requires is what this repository implements; the review's acceptance and the resolution question are the maintainer's call |
| Licence | MIT (weights, the upstream `aurora` code and this repository's dependencies) — use, modification, redistribution and commercial use permitted with the licence and notices preserved |
| Weights | Would be redistributed converted, not unmodified: the served artifacts are the deterministic safetensors derived from the pinned pickles, with both identities recorded (asset spec §11.2); this repository redistributes neither |
| Remote code | **Not required** — no Hub-hosted module is imported; the model class comes from `microsoft-aurora==2.0.1` on PyPI |
| Executable serialization | Two pickles, each unpickled **once** at conversion through a restricted loader after a digest check and a static audit; a DIMER profile should carry the two safetensors files and never the pickles |
| Runtime | `microsoft-aurora==2.0.1` + `torch==2.14.0` + `timm` + `einops` (+ `xarray`/`netCDF4` for NetCDF I/O, `numcodecs` for the tutorial data); float32; CPU sufficient at coarse resolution, GPU advisable at 0.25° |
| Upload format | `aurora-0.25-small-pretrained.safetensors` (451,230,408 bytes, SHA-256 `fc03b5fc…`) + `aurora-0.25-static.safetensors` (12,459,136 bytes, SHA-256 `9bd430b6…`); **the `.ckpt` and `.pickle` files must not be uploaded** |
| Input contract | Windows as `{lat, lon, levels, times, surf, atmos, static}` mappings or NetCDF; global equiangular grid, 13 standard levels, 6-hourly, SI units; static fields on the input grid (the native ones are served for 0.25°) |
| Resolution | Served at whatever global grid the caller supplies within the ceilings; only 0.25° is in-distribution, and the tutorial's 1.5° numbers must not be read as the model's skill |

**Two things are open, and neither is the licence or the code.** First, the trust boundary: whether a one-time unpickle through torch's weights-only unpickler (checkpoint) and a two-name `find_class` allow-list (static fields), after static audits with pinned digests — in the build and in the tutorial runtime, where the notebook converts what it downloads — meets the DIMER bar, or whether DIMER should host only the safetensors converted and verified once by the maintainer. Second, the operational tier: the inventory records the small checkpoint as the practical first E2E route and the 5 GB full checkpoint as HPC-tier; this profile delivers the small route at a coarse grid with the native-resolution path tested only through upstream's 400 × 800 fixture, and a native 0.25° hosted profile would need a GPU worker and static fields the pipeline already serves. The served artifacts are the same files either way.
