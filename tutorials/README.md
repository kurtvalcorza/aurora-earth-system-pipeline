## Two things this tutorial does that the fleet's others do not

**It fetches its dataset from pinned objects, not from a package or a Hub file.** The default data is real ERA5 reanalysis served by WeatherBench 2's public bucket; every Zarr chunk, `.zarray` descriptor and coordinate the notebook touches is pinned by byte size and SHA-256 in the carried `samples.py`, refused on mismatch before decoding, and decoded with `numcodecs` only. The generator's *External access* bullet names the Hub; the template adds a second bullet naming the bucket, the byte count and the Copernicus licence.

**It measures the model out of distribution and says so.** The small checkpoint runs at 1.5°, six times coarser than its training grid, so the frozen model's error against persistence is an honest negative number printed before any adaptation, and the adapted number is read against both. Nothing in the notebook is a claim about Aurora at its native resolution; the converted model's faithfulness at native-resolution class is established in `docs/WEIGHTS.md` with upstream's own regression fixture.

## Conformance notes

- **Standalone carrier (ST1–ST8):** the primary path performs no clone, repository install, or repository import. Section 2 embeds the repository's 3 modules (`pipeline.py`, `samples.py`, `metrics.py`) verbatim in topological dependency order (each tagged `metadata.dimer.embedded_module`; the only rewrites make `DEFAULT_WEIGHTS_DIR` working-directory-relative and remove internal relative package imports), Section 3 carries the 3-file snapshot manifest inline and asserts it against the module's constants before fetching, and `NOTEBOOK_SOURCE` records the repository, revision and module digests in the exports.
- **Parity (PAR1–PAR4):** `tests/test_notebook_parity.py` and `tools/validate_release_assets.py` fail when the carried modules, the inline manifest, or the inline pins differ from the repository, or when the notebook is not byte-identical to the generator's output.
- **Model acquisition (MOD1–MOD9):** `stage_missing_files(WEIGHTS_DIR, allow_download=True)` fetches only the manifest entries that are absent, from the Hugging Face Hub at the immutable revision (never `main`); `verify_snapshot` re-hashes all three entries and asserts both source digests against the package constants; `AuroraPipeline.from_pretrained(weights_dir=..., use_lora=True)` audits and converts both pickles when the safetensors are absent, verifies them against pinned digests, builds the model from `microsoft-aurora` and loads strictly with the 80 LoRA tensors at zero. Each pickle is unpickled exactly once, in that conversion, through a restricted loader, after the audit.
- **Stages (§4.1):** `fetch_sample_dataset` / `load_byod_dataset` (sample acquisition) → `validate_dataset` + `validate_inputs` refusal probes (validation, with the ceilings and a dataset digest) → role assignment by window (train / validation / test from distinct years) → `pipe.predict` roll-out with the determinism assertion (inference) → `persistence_only` + `pipe.evaluate` on the frozen model (baselines) → `pipe.adapt` (bounded LoRA fine-tuning) → `pipe.evaluate` on validation and test with the three-way comparison (evaluation) → `pipe.predict` from a new origin (inference) → `pipe.save_artifact` → `AuroraPipeline.from_artifact` with the parity assertion (export and reload).
- **Score semantics (UNC1–UNC4):** the outputs are continuous gridded fields with no threshold and no forecast uncertainty; the notebook states that RMSE against ERA5 inherits ERA5's own errors, that roll-outs accumulate error, and that the adapted model may be worse than the foundation model away from the training windows.
- **Baselines and evidence (EVAL6/EVAL10/EVAL11):** the persistence baseline and the frozen model are scored on the same origins and leads as the adapted model, and every metric is labelled as tutorial sample-sanity evidence from one two-day window per role with no dispersion estimate. The notebook explains why persistence for 2 m temperature improves again at 24 h (the diurnal cycle) so the baseline is read as a baseline, not a straw man.
- **Split integrity (SPL1–SPL8):** roles are assigned by window from three different years and seasons, never by shuffling steps; validation metrics select the epoch and the test window is used for nothing but the final evaluation. The notebook states that consecutive analyses are near-duplicates and that real data must be split by period. In BYOD mode one window plays every role and the notebook says the held-out numbers are then not independent.
- **Ceilings (VAL6):** the grid bounds, the patch-size rules, the 13-level set, the 3..64-step and 6-hour-spacing rules, the 8-step roll-out limit and the plausibility ranges are stated in the Prerequisites and printed from the schema before the model runs; four refusals are demonstrated.
- **BYOD (DAT10–DAT19):** `USE_BYOD` defaults to `False` so the sample path never opens an upload dialog; when enabled, user data flows through the same validation, baselines, adaptation, evaluation, inference, export and reload cells. The expected NetCDF schema, the grid rules and the privacy guidance — proprietary analyses and embargoed datasets are restricted data — are stated in the Prerequisites and in Section 4, and a sample window is written to `outputs/aurora_earth_system_sample_window.nc` in that shape.
- `tools/validate_release_assets.py` performs source validation only. It does not satisfy the clean-runtime execution requirement; a release review must confirm that a recorded clean run in `../docs/release-verification.md` matches the notebook revision under review before the status is promoted to `Release-grade`.
