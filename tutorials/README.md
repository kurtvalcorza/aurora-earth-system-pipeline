## Two things this tutorial does that the fleet's others do not

**It fetches its dataset from pinned objects, not from a package or a Hub file.** The default data is real ERA5 reanalysis served by WeatherBench 2's public bucket; every Zarr chunk, `.zarray` descriptor and coordinate the notebook touches is pinned by byte size and SHA-256 in the carried `samples.py`, refused on mismatch before decoding, and decoded with `numcodecs` only. The generator's *External access* bullet names the Hub; the template adds a second bullet naming the bucket, the byte count and the Copernicus licence.

**It measures the model out of distribution and says so.** The small checkpoint runs at 1.5°, six times coarser than its training grid, so the frozen model's error against persistence is an honest negative number printed before any adaptation, and the adapted number is read against both. Nothing in the notebook is a claim about Aurora at its native resolution; the converted model's faithfulness at native-resolution class is established in `docs/WEIGHTS.md` with upstream's own regression fixture.

## Conformance notes

- **Standalone carrier (ST1–ST8, SRC4):** the primary path performs no clone, repository install, or repository import. Section 2 carries `src/aurora_earth_system_pipeline/` (4 modules), `tutorial_stages.py`, `requirements.txt` (the lock), the snapshot manifest, the licence and `source.json`; each is written to a fresh run directory and verified against `CARRIED_HASHES` before use, and `NOTEBOOK_SOURCE` records the repository, revision and file digests in the exports.
- **Parity (PAR1–PAR4):** `tests/test_notebook_parity.py` and `tools/validate_release_assets.py` fail when a carried file differs from the repository, when the lock does not pin every `pyproject.toml` pin with hashes, or when the notebook is not byte-identical to the generator's output.
- **One-pass Run all (RUN1, RUN10, ENV6):** nothing is installed into the kernel; the pinned `uv` wheel is checked by size and SHA-256, builds a managed CPython 3.12.12 venv and installs the lock with `--require-hashes --only-binary :all:`; the `runtime` stage refuses a version that differs from the lock.
- **Model acquisition (MOD1–MOD9):** the `weights` stage fetches only the manifest entries that are absent, from the Hugging Face Hub at the immutable revision (never `main`), re-hashes them, audits both pickles statically against allow-lists and converts each exactly once through a restricted loader into safetensors with pinned digests. Every later stage loads only the safetensors.
- **Stages (§4.1):** `data` (sample acquisition or BYOD, `validate_dataset` + `validate_inputs`, the workflow-length check, roles, sample NetCDF, five refusal probes) → `rollout` (frozen roll-out with the determinism check) → `frozen` (`persistence_only` + frozen `evaluate`, written before adaptation) → `adapt` (fresh frozen pipeline, bounded LoRA fine-tuning, adapter export) → `evaluate` (adapter rebuilt from files; three-way comparison) → `forecast` (new origin, NetCDF export) → `reload` (fresh process, forecast parity) → `bundle`; optional `activity`.
- **Reruns start from the frozen model (DAT13, DAT14):** each stage that runs the model builds it from the verified files in its own process; `AuroraPipeline.adapt` refuses an already-adapted pipeline; re-running Section 5 clears every later result, and a later stage refuses an adapter trained on other data or settings.
- **Score semantics (UNC1–UNC4):** the outputs are continuous gridded fields with no threshold and no forecast uncertainty; the notebook states that roll-outs accumulate error and that the adapted model may be worse than the foundation model away from the training windows.
- **Baselines and evidence (EVAL6/EVAL10/EVAL11):** persistence and the frozen model are scored on the same origins and leads as the adapted model; every metric is labelled tutorial sample-sanity evidence from one window per role with no dispersion estimate. The outcome is printed, not asserted, except on the default configuration, where the recorded runs improve.
- **Split integrity and pretraining overlap (SPL1–SPL8, DAT9):** roles are assigned by window from three different years and seasons, never by shuffling steps; validation selects the epoch and the test window is used only for the final evaluation. Upstream does not publish the small checkpoint's training period, so the notebook states that overlap of the 2018–2021 sample with pretraining cannot be ruled out. In BYOD mode one window plays every role and the notebook says the held-out numbers are then not independent.
- **Ceilings (VAL6, VAL7):** the grid bounds, the 13-level set, the 6-hour spacing, the 8-step roll-out limit and the plausibility ranges are printed from the schema; the test window must hold 2 + max(`ROLLOUT_STEPS`, `MAX_LEAD_STEPS`) steps and `ORIGIN` must lie inside it, checked in Section 5 before any model runs; five refusals are demonstrated.
- **BYOD (DAT10–DAT19, EXE1/EXE2):** `USE_BYOD` defaults to `False`; `BYOD_PATH` works on any runtime and the upload dialog is used only on Colab with the field empty. The sample file Section 5 writes is a valid BYOD input of exactly the length the settings need.
- **Guided layer (GDL1–GDL15):** how to use, input → model → output, roadmap, fast path, glossary, section tags, prediction prompts, checkpoints with collapsed answers, an optional Predict → Change → Run → Observe → Explain activity (adaptation scope, off by default, writes only under `outputs/activity/`), troubleshooting and a conclusion template; infrastructure cells are titled and collapsed.
- `tools/validate_release_assets.py` performs source validation only. It does not satisfy the clean-runtime execution requirement; a release review must confirm that a recorded one-pass clean run in `../docs/release-verification.md` matches the notebook revision under review before the status is promoted to `Release-grade`.
